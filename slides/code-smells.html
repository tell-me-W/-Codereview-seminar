01

Bloaters
너무 커져서 다루기 어려운 코드

크기 자체보다 책임과 변경 이유가 함께 부풀었는지 본다.

Bloaters

긴 메서드는 흐름을 숨긴다

Before.javaLong Method
public void onMessage(TibrvMsg msg) {
    validateHeader(msg);
    loadAccount(msg);
    calculateTrade(msg);
    saveTrade(msg);
    publishResult(msg);
    writeAuditLog(msg);
}

질문

  • 메서드 이름 하나로 책임이 설명되는가?
  • 핵심 계산만 테스트하기 쉬운가?
  • 메시지 필드 규칙이 곳곳에 퍼졌는가?

Before.javarepeated branch
if (type == ORDER) {
    order(msg);

확인할 축

  • 새 타입이 계속 추가되는가?
  • 분기 규칙이 여러 메서드에 복제되는가?
  • 핸들러, 전략, 다형성 중 무엇이 실제로 범위를 줄이는가?

리뷰에서 묻기

  • 이번 요구사항으로 어떤 파일이 같이 바뀌었나?
  • 변경 이유별 책임이 모여 있나?

Nuance

스멜을 규칙으로 오해하지 않기

항목의심할 때남겨도 되는 자리

Data Class도메인 행동이 서비스로만 몰림DTO, 메시지 모델, API 경계

Review Checklist

리뷰에서 바로 묻는 질문

  • 이 클래스는 몇 가지 이유로 바뀌는가?
  • 같은 변경 때문에 여러 파일을 만지는가?
  • 새 조건을 넣을 때 같은 분기를 반복 수정하는가?
  • 테스트보다 외부 의존성 준비가 더 어려운가?
  • 데이터를 가진 객체보다 남의 필드를 더 묻는가?
  • 지금 추상화가 실제 변경 범위를 줄이는가?
