01

테스트가 없으면
기억이 품질 시스템이 된다

수동 확인, 경험, 배포 전 불안이 검증을 대신한다.

Why Test

수동 확인과 자동 검증의 차이

수동 검증

  • 확인 범위가 사람 기억에 의존
  • 반복할수록 빠뜨릴 확률 증가
  • 리뷰에 안전 근거가 부족
  • 배포 직전 확인 비용이 큼

자동 테스트

  • 같은 검증을 다시 실행
  • 기존 동작을 문서처럼 보존
  • 리뷰에서 변경 의도를 보강
  • 회귀 버그를 빠르게 신호
Value

테스트 코드는 품질 문서다

Safety

변경 후에도 동작을 지키는 안전망

Review

리뷰어가 확인할 수 있는 실행 근거

Document

기존 규칙을 코드 예제로 설명


"작은 수정"이라는 말보다
실행 가능한 검증이 더 강하다.

02

검증을 실행하는 틀

버전 차이보다 중요한 것은 준비, 실행, 확인의 구조다.

JUnit

given / when / then으로 읽는다

PriceCalculatorTest.javaJUnit
@Test
public void calculate_discountApplied_returnsDiscountedPrice() {
    // given
    int price = 10000;
    int discountRate = 10;

    // when
    int result = calculator.calculate(price, discountRate);

    // then
    assertEquals(9000, result);
}

03

좋은 테스트의 기준
FIRST

빨리 돌고, 독립적이고, 결과를 스스로 말해야 한다.

FIRST

테스트를 믿게 만드는 다섯 조건

Fast

자주 실행할 만큼 빠르게

Independent

순서와 다른 테스트에 독립

Repeatable

시간, PC, 외부 응답에 흔들리지 않게

Self-Validating

assert로 성공과 실패를 직접 판단

Timely

변경 시점에 가까이 작성

Stability

흔들리는 입력은 통제한다

의존성문제테스트 방향
현재 시간실행 시점마다 결과 변화Time Provider 분리
DB / API속도, 장애, 데이터 상태 영향Mock 또는 계층 분리
랜덤값재현 어려움고정 입력 주입
04

의존성을 제어해야
로직이 보인다

Mock은 집중을 돕고, PowerMock은 레거시의 현실을 버틴다.

Mock

테스트 대상만 남기기

Mock이 줄이는 것

  • DB 상태 준비
  • 외부 API 응답 대기
  • 예외 상황 재현 비용
UserServiceTest.javaMockito
when(userRepository.findById(1L))
        .thenReturn(user);

User result = userService.findUser(1L);

assertEquals("kim", result.getName());
PowerMock

레거시에서는 교체할 틈이 없다

테스트를 막는 구조

  • static 직접 호출
  • private 안에 핵심 로직
  • new 생성자 고정
  • final 의존

PowerMock을 보는 관점

  • 당장 필요한 현실적 다리
  • 강력하지만 구현 세부사항에 결합
  • 신규 코드의 기본값은 아님
  • 분리와 DI의 필요 신호
