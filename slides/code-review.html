02

좋은 코드리뷰는 능력이 아니라 설계다

리뷰 기준, PR 설명, 체크리스트가 누락을 줄인다.

Failure Pattern

리뷰가 약해지는 세 가지 이유

기준 부재

사람마다 중요하게 보는 것이 다르다.

스타일 편향

핵심 리스크보다 취향 평가가 많아진다.

실패 관점 부재

정상 흐름만 보고 장애 시나리오를 놓친다.

Review Priority

먼저 볼 것은 위험한 변경

관점확인 질문
동작 영향기존 기능의 흐름이나 예외 처리가 바뀌는가?
데이터 영향저장, 수정, 삭제, DB Script가 포함되는가?
외부 연동API, 메시지, timeout, retry 처리가 바뀌는가?
테스트핵심 로직과 재발 방지 테스트가 있는가?
03

PR 설명, Markdown, Files changed, Suggestion이 리뷰 품질을 만든다.

PR Template

PR 설명은 리뷰의 입구다

.github/pull_request_template.mdexample
## PR 개요
- 어떤 작업을 했는지 설명해주세요.

## 관련 이슈
- SR No:
- Patch Item No:

## 체크리스트
- [ ] 테스트 또는 수동 검증 완료
- [ ] 영향 범위 작성
- [ ] 리뷰어 참고 사항 작성

04

좋은 리뷰 코멘트 작성법

문제, 이유, 제안을 함께 적는다.

Comment Quality

평가가 아니라 피드백으로 쓴다

피해야 할 표현

  • 이건 별로입니다.
  • 왜 이렇게 했나요?
  • 이렇게 하지 마세요.

좋은 구조

  • 무엇이 문제인지
  • 왜 위험한지
  • 어떻게 바꿀 수 있는지
Team Rule

우리 팀에서 바로 적용할 기준

  • PR 작성자는 변경 목적과 영향 범위를 적는다.
  • 리뷰어는 스타일보다 동작 영향과 실패 흐름을 먼저 본다.
  • 단순 수정은 Suggestion으로 제안한다.
  • 반복되는 지적은 PR 템플릿에 반영한다.
  • 버그 수정에는 재발 방지 테스트를 확인한다.
  • 논의된 결정은 PR 기록에 남긴다.
Takeaway

코드리뷰는 팀의 변경 안전장치다
